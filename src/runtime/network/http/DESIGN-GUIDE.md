## HTTP 模块

一个实用的分层：

```plantuml
业务动作
  ↓
领域 API（createOrder / sendMessage）
  ↓
数据层缓存与状态管理（Query / Mutation）
  ↓
HTTP Transport（鉴权、超时、取消、错误归一、trace、重试）
  ↓
fetch / XHR
```

HTTP Transport模块是前端与服务端之间的可靠通信边界，用来统一解决契约、鉴权、错误、重试、可观测性和数据安全，业务代码只表达“要做什么”。
核心原则：读请求追求可缓存、可取消、可重试；写请求优先保证幂等、可追踪、不会重复提交；最终事实始终由服务端决定。 离线补偿、取消和异步任务状态也应以服务端的权威状态为准。

## 关键职责

### 请求与响应契约

- 统一 Base URL、环境配置、超时、请求方法、Query、JSON/FormData/文件上传等编码规则。
- 统一响应信封与错误格式，例如业务成功不等于 HTTP 200；必须能区分参数错误、未登录、无权限、限流、服务端错误。
- 在边界做运行时校验（如 Zod/Valibot），防止后端字段变更后错误数据扩散到 UI。
- 类型应描述“服务端真实协议”，不要只靠泛型假定返回值正确。

### 身份、权限与安全

- 统一附加认证信息：Cookie 会话或 Bearer Token；不要让业务代码自行拼 Authorization。
- 处理 Token 刷新与并发请求：刷新期间其余请求等待同一个刷新 Promise，避免同时触发多次刷新。
- 刷新失败后清理本地身份状态、跳转登录，并保留登录后回跳地址。
- 明确 CSRF、跨域、Cookie 的 SameSite/Secure/HttpOnly 策略；敏感令牌不能随意存进 localStorage。
- 日志、埋点、错误上报必须脱敏：Authorization、Cookie、密码、验证码、身份证号等不能上传。

### 可靠性与幂等性

- 取消请求：页面卸载、搜索词变化、路由切换时，用 AbortController 取消已无意义的请求。
- 超时：区分连接超时与整体响应超时，并保证超时会真正中止请求。
- 重试：只对可安全重试的请求做有限重试，例如网络错误、短暂 5xx、429；使用指数退避和随机抖动，避免流量雪崩。
- 写操作默认不能盲重试。创建订单、发消息、提交任务等应由客户端生成并稳定携带 Idempotency-Key，服务端据此去重。
- 对离线或弱网下必须送达的操作，使用持久化 Outbox：保存请求意图、幂等键、状态和重试次数；网络恢复后顺序补偿。不要把二进制大文件或秘密直接塞入 Outbox。

### 错误模型与用户体验

建议将错误标准化为业务可消费的对象，而不是到处 catch (error)：

```typescript
type HttpError =
  | { kind: "network"; retryable: true }
  | { kind: "timeout"; retryable: true }
  | { kind: "http"; status: number; code?: string; message: string }
  | { kind: "business"; code: string; message: string; fieldErrors?: Record<string, string> }
  | { kind: "cancelled" };
```
业务层据此决定体验：
- 表单字段错误：显示在字段旁。
- 400：提示用户修正参数。
- 401：刷新身份或引导登录。
- 403：告知无权限，不要无限重试。
- 429：提示稍后再试，并尊重 Retry-After。
- 网络失败：显示可恢复状态”。
- 请求取消取消：通常静默，不作为错误弹窗。

### 并发与数据一致性

- 同一个资源的重复读请求可去重；但要避免把本应独立的请求错误合并。
- 对搜索、筛选等“后发结果应覆盖先发结果”的场景，用取消或请求序号避免旧响应覆盖新 UI。
- 对编辑、保存等写操作，引入版本号 / ETag / If-Match，让服务端检测并发修改，不能静默覆盖。
- 缓存要有明确策略：哪些可缓存、多久有效、如何失效、突变后更新哪些缓存。HTTP 模块负责传输语义，服务端状态缓存通常交给 TanStack Query/SWR 等上层数据层管理。

### 可观测性与治理

- 每个请求带 traceId / requestId，与后端日志、网关和异步任务链路关联。
- 采集延迟、失败率、超时率、重试次数、接口/错误码分布；不要只记录“请求失败”。
- 支持灰度和服务端能力降级，例如功能开关、模型或服务不可用时的明确 fallback。
- 对接口按域拆分 client（认证、用户、订单、任务等），共享底层 transport；不要做一个无限膨胀的 api.ts。

### 一组容易忽略的边界（Special Cases）
> 可暂时不实现，SSE/WebSocket会有单独的模块处理，文件上传下载后续可再基于扩展考虑。
> GraphQL / RPC 后续可再基于扩展考虑。

- 文件上传：进度、取消、大小/类型校验、分片/预签名上传、失败续传策略。
- 下载：鉴权、文件名解析、流式处理、大文件内存控制。
- GraphQL / RPC：同样需要超时、取消、鉴权、错误规范化、重试与观测；协议不同，生产问题相同。
- SSE/WebSocket 不是普通 HTTP 请求：断线恢复、游标、事件去重、服务端回放与客户端持久化进度需要单独设计，不能只靠浏览器自动重连。
